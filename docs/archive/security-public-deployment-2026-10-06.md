# 公网部署安全初审（2026-10-06）

## 结论与范围

当前已有账户、服务端身份、角色、实时场景授权、发布快照、本人任务/素材隔离和 revision 保护，但不能据此直接宣布适合公网部署。建议先完成公网安全加固，再小范围邀请制开放。

本报告是当前工作区代码初审，不是完整渗透测试或生产验收。没有读取生产密钥/数据库，没有扫描公网、改生产配置、重启后台/Hermes/ComfyUI，也没有调用真实模型、生成业务媒体或审批生产任务。工作区有大量既存未提交改动；本次只新增本报告，未修改业务代码。

威胁范围包括匿名请求、有效但恶意的普通用户、跨用户访问、伪造代理头、恶意媒体、模型输出和提示词注入。管理员账户被盗需要同时考虑；不把管理员可调用的任意本机能力视为适合向所有互联网用户开放的能力。

优先级：P0 为公网开放前必须解决或明确隔离的项目；P1 为小范围开放前的配套加固。下表区分已确认缺口与待核查条件风险。

## 已存在且本次回归通过的基础

- `server/services/accessService.ts`：密码使用带随机盐的 scrypt；凭证使用随机令牌并保存摘要；账户禁用/密码或角色变化使旧凭证失效。
- `server/services/userPortalService.ts`：普通用户用服务端固定发布快照提交；媒体输入限定本人固定版本素材，不允许直接提交路径或 URL。
- 管理 API、旧入口、媒体 HEAD/Range、异步落库/入队有现有授权机制；不能因公网加固改成只检查页面或客户端身份。
- 真实 stdio MCP 复用 HTTP 与业务服务的权限；没有理由再建 AI 旁路任务库。
- 已有素材媒体响应设置 nosniff 和 sandbox CSP（`server/api/assetRoutes.ts:70`），因此不能将“上传扩展名校验不足”直接等同于已证明的同源脚本执行。

## P0：公网开放门槛

### 1. 首次管理员初始化不能只信任本机来源（已隔离复现，条件触发）

证据：`server/api/accessRoutes.ts:19-23` 只检查 `req.ip` 是否回环地址；Origin 缺省时允许继续。当前应用未设置可信反向代理。

条件：管理员尚未初始化，且公网反向代理/穿透代理从本机连接 Node，且代理没有禁止 setup 路径。此时公网客户端省略 Origin，应用可能把它当成本机初始化请求。不是对已初始化账户的密码绕过。

建议：

- 公网开放前先在私有通道完成初始化；公网代理明确拒绝 `/api/auth/setup`。
- 应用端增加显式初始化开关/一次性受控机制，默认关闭；初始化成功后不再可用。不能把仅设置 trust proxy 当作完整修复。
- 转发头必须由可信代理覆盖；客户端不能自报本机地址获得初始化权限。
- 代理拦截是纵深防御，不应是应用唯一防线。

验收：代理连接、伪造 X-Forwarded-For、缺省 Origin、初始化关闭和重复初始化均不能建立未授权管理员；私有受控初始化仍可正常完成。

### 2. HTTPS、可信代理、Origin 和 Cookie 必须一起设计（已隔离复现）

证据：`server/api/accessRoutes.ts:15,25` 依据 `req.secure` 设置 Cookie；登录和 `server/services/accessService.ts:133` 将 Origin 与 `req.protocol + Host` 比较。当前未见 trust proxy 或固定公网 Origin 配置。

在 TLS 终止后代理通过 HTTP 回源的默认配置下：

- 带 `Origin: https://studio.example` 的模拟浏览器登录返回 403 `INVALID_REQUEST_ORIGIN`。
- 不带 Origin 的模拟登录成功，但 Cookie 缺少 Secure。

建议：

- 明确一个受控公网 Origin 和允许的 Host；公网模式要求 HTTPS、Secure Cookie，保留 HttpOnly/SameSite。
- 仅信任精确的代理地址/网络拓扑；不要无条件 `trust proxy = true`。应用回源端口必须不可被公网客户端绕过。
- Cookie 写入与 Bearer AI 请求明确区分：浏览器写入有一致的来源/CSRF 策略；不能为了“修好 HTTPS 登录”直接删除来源校验或开放任意 CORS。
- 不能以“存在任意 Authorization 头”作为绕过 Cookie CSRF 校验的充分条件，应依据实际被验证的凭证路径。
- 代理清理/覆盖 Forwarded 和 X-Forwarded-*；验证伪造头不能改变协议、来源和限流身份。

### 3. 登录抗暴力破解与匿名资源保护（代码缺口）

证据：`server/services/accessService.ts:77-84` 每次登录执行 scrypt；登录路由未见节流。`server/index.ts:93` 的 16MB JSON 解析位于鉴权之前。

建议：代理层限制连接、请求速率、头/体积和超时；应用层按可信客户端来源与账户组合节流登录，限制并行密码校验。响应使用稳定错误码、429 和 Retry-After；避免永久锁账户造成拒绝服务。仅按客户端自填 X-Forwarded-For 限流无效。

管理端先限制私有访问，外网管理另加 MFA/独立身份验证措施。不要只封 `/admin` 页面而仍公开所有管理 API。

验收：连续失败被限制、并行登录不能无限占用密码线程池；正常账户可恢复登录；伪造代理头不能绕过限流。

### 4. 执行并发不等于用户额度或队列上限（代码缺口）

证据：`server/services/runService.ts:42,55,103-138` 有内存队列和执行并发上限，但提交未见全局/用户队列容量与调用额度检查。

建议：

- 设置每用户正在准备/排队/运行数量上限和全局容量；不能只限制实际 GPU 执行数量。
- 设置用户每日调用额度、最大输入规模、单任务遍历项/总执行步骤/最长运行时间，并限制生成数量、分辨率、帧数等资源放大参数。
- 提交、审核继续生成、续跑等所有执行入口复用同一权威准入服务；入队前原子占用，失败/取消/重启可对账，防止并发穿透和额度泄漏。
- 额度、预留与使用记录进入现有权威 SQLite，不另建浏览器或 AI 数据库。
- 同一 runId 的回执丢失先对账，不能再扣额度或盲目生成新任务。
- 执行步骤还需有内存/CPU/磁盘/GPU资源边界及紧急停止生成的运维措施。

验收：并发超限只接受允许数量；重启后额度/占用一致；回执丢失、旧 revision、取消、失败、等待审核和恢复均可对账。

### 5. 上传与媒体读取不能只有限制单文件大小（代码缺口）

证据：`server/api/accessRoutes.ts:79` 使用 `express.raw` 缓冲至 250MB；`server/services/assetService.ts:144-161` 流式写入有单文件限制，但后缀来自客户端文件名，未见在该保存路径上验证内容/声明类型匹配及用户总配额。`server/index.ts:1675` 在 arrayBuffer 完整读取后再检查实际字节数。

建议：

- 上传按类型设置大小、次数和并发上限；设置用户总存储配额和全局剩余磁盘门槛。
- 校验实际内容与媒体类型，限制图片像素、视频时长/帧数、解码资源；原始解析放低权限受限环境，不能仅信任后缀/MIME。
- 大文件使用有界流式处理；远程媒体无 Content-Length 或虚假 Content-Length 时也要逐块限制，超限立即终止。
- 媒体响应统一安全头，不将用户内容当可执行 HTML；归档、预览、代理、HEAD/Range 都不能失去授权。
- 临时文件、失败上传和预留配额要回收；清理不能删除其他任务或其他用户的数据。

### 6. 公网业务生成与高权限 Hermes 必须隔离（条件风险，尚未验证生产配置）

证据：`server/index.ts:1909-1923` 将用户相关内容交给 `hermes-agent`；仓库存在通过管理工具组织、配置工作台业务的 Hermes profile 设计。没有读取实际启用 profile 的凭证/工具配置，不能据此宣称普通用户已可提权。

若公开场景使用带工作台管理员 token、shell、任意文件、开发工具、飞书写入或其他高权限 MCP 的 profile，HTTP 的普通用户授权不能约束 Agent 在模型内部调用的这些工具。提示词“不要越权”不是权限隔离。

建议：

- 用户输入/媒体/模型输出都作为不可信数据；公开生成使用独立低权限执行环境和最小工具集合，无工作台管理凭证。
- 业务管理员协作 profile 与公网内容生成 profile 分离；通过支持的用户配置建立，不修改 Hermes 上游或 evolution foundation。
- 如果不能证明公开场景所需权限已被限制，先禁用该场景的公网生成，而不是靠文案宣称安全。
- 保持一套场景与权威服务；隔离执行权限不等于创建个人/共享场景工作区。

验收：使用假模型/假工具的攻击输入不能调用管理工具、读无关文件或访问其他用户数据；无需调用真实模型或审批生产任务。

### 7. 服务端抓取和本机文件读取需统一信任边界（代码存在，用户可达性待追踪）

证据：`server/services/assetService.ts:129` 直接 fetch 来源 URL，其他媒体执行路径也有抓取；当前普通用户媒体输入已限定本人素材，不能把管理员抓取能力直接称为匿名 SSRF。

建议区分受信的 ComfyUI/Hermes 本地配置与用户/模型产生的任意 URL。后者限制协议、目标主机与解析 IP，逐次检查重定向，防止访问云 metadata、环回/内网和非业务端口；仅在初始 URL 做字符串匹配不足。受信的本地服务通过显式白名单保留，不能一刀切禁掉所有本地地址而破坏业务。

同样审查“文本/JSON 输入→媒体 locator→本机读取”的间接路径及符号链接边界，证明只能读授权素材/运行产物。尚未完成所有公开发布工作流的数据流追踪。

## P1：配套加固

- **监听与网络**：`server/config.ts:82` 正式模式缺省监听 0.0.0.0。同机反代/穿透建议显式监听 127.0.0.1；跨机回源使用受控私有网络/认证通道。只公开 HTTPS 入口，不公开 Node、ComfyUI、Hermes、Vite、SQLite、数据目录或备份。监听地址本身不等于已证明公网暴露，仍需核验防火墙/隧道配置。
- **错误脱敏**：`server/index.ts:2305` 将未知异常的 error.message 直接返回客户端；生产未知错误应返回通用消息、稳定 code/requestId，细节仅写受控日志。业务参数错误保留可操作语义，不能全部变成黑盒。
- **公开探针最小化**：`server/index.ts:1994` 的匿名 health 包含适配器和能力版本；公网只需最小存活信息，详细运维指标留受控入口。
- **页面/媒体安全头**：已有素材媒体 CSP，但未见统一页面 CSP、frame-ancestors、nosniff 等策略；HTTPS 入口配 HSTS 前先确认域名与子域影响。CSP 验证应覆盖实际 React 页面及媒体，不凭模板宣称完成。
- **审计与告警**：现有请求日志应补安全事件（登录失败/节流、凭证创建/吊销、授权变更、发布、配额拒绝、越权），记录可信主体/结果/requestId，禁止日志保存密码、Authorization、Cookie、完整 token 或敏感输入。设置异常告警和日志保留策略。
- **凭证**：公网业务生成不能持有应急全权 ZANE_ADMIN_TOKEN；正常账户令牌已可撤销。按实际需要评估短期凭证、工具权限范围、管理 MFA，不能把凭证明文放 URL/前端持久化或备份公开目录。
- **部署与恢复**：冻结明确代码版本，先在临时项目/端口验收；正式升级核验进程身份、空闲/待审核任务与 SQLite/配置备份，使用现有安全升级机制。验证恢复演练及备份私密性；不连带重启 Hermes/ComfyUI。
- **依赖**：本次生产依赖 npm audit 报告为 0，不代表应用无漏洞；没有自动升级依赖或改 lockfile。生产只发布构建产物，不把开发服务器当公网服务。

## 推荐首发拓扑（尚未部署）

公网用户 → HTTPS 反向代理/穿透入口（入口限流、固定 Host、覆盖代理头、禁 setup）→ 私有回源工作台 → 现有权威服务/SQLite → 低权限执行环境 → 私有 ComfyUI/Hermes。

管理端走 VPN/私有入口或独立受控网关；管理页面与管理 API/MCP 一起控制。用户端与 AI 操作面仍服从服务端身份和实时授权；不是另建一套工作区。

建议第一阶段邀请制：管理员建号并分配已发布场景，不新增开放注册。邀请码/自助注册/计费等属于额外业务能力，需另做滥用、恢复和隐私设计。
