# 用户入口部署与本轮安全边界

## 本轮范围

按当前确认只做三项：**只公开用户入口及必要API、登录限流、错误脱敏**。未增加任务/费用额度、上传配额/内容校验或Agent执行隔离。初始代码验收未改生产配置；随后按用户明确要求完成本机正式启用，详见文末启用记录。公网域名、穿透及HTTPS代理尚未配置。

用户入口不是“隐藏管理员按钮”：服务端先检查明确的路径/方法白名单，再执行现有身份、本人归属与场景授权。初始化、管理页面/API、旧管理接口和管理员/应急凭证在该入口不可用。

两个监听入口属于同一Node进程，复用同一AccessService、工作台服务、状态机和SQLite；没有新增场景库、个人/共享工作区或AI旁路任务数据库。共用前端构建，管理组件代码可能仍包含在JS产物中，但不能获得管理页面/API访问权限；不是物理拆分的前端发布包。

## 可选配置：默认不启用

在正式部署配置中**明确确认**如下设置，之后按现有升级流程发布；2026-10-06已在本机 `.env.production.local` 启用这些配置（默认行为仍为不启用）：

```dotenv
API_HOST=127.0.0.1
API_PORT=8799
ZANE_PUBLIC_USER_HOST=127.0.0.1
ZANE_PUBLIC_USER_PORT=8800

ZANE_LOGIN_WINDOW_SECONDS=900
ZANE_LOGIN_ACCOUNT_ATTEMPTS=8
ZANE_LOGIN_SOURCE_ATTEMPTS=30
ZANE_LOGIN_MAX_CONCURRENT=4
```

- `ZANE_PUBLIC_USER_PORT` 留空时原单入口行为保留。开启时 `API_HOST` 必须为 `127.0.0.1`、`::1` 或 `localhost`，否则启动直接失败，不允许同时把管理监听公开。用户端口不得与非零管理端口相同；端口0仅供隔离测试。
- 同机代理/穿透只回源到用户端口8800；管理端口8799仅走本机/私有入口，不能另外建立公网转发。跨机代理如何访问回源属于实际网络配置，不能直接把管理端口改为0.0.0.0。
- 首个管理员仍由私有入口按现有流程建立，再创建普通用户并分配已发布场景。未初始化的用户入口只显示“联系管理员”，不提供创建管理员表单。
- 管理员仍在私有入口使用管理UI/HTTP/MCP。公网入口拒绝管理员会话、管理员API token和应急token，即便请求的是 `/api/v1/self/account`；不会因共享cookie或伪造请求头变成管理入口。
- 公私入口建议使用不同主机名，避免同一主机名不同端口的cookie互相影响；cookie不按端口隔离。前端仍按身份隔离防丢outbox。

### 用户客户端与AI接入

浏览器访问用户入口 `/app`；根路径重定向到 `/app`。用户端保留登录、已授权场景、本人草稿/任务/素材、账户和本人AI接入等现有能力。

普通用户MCP客户端将 `ZANE_BASE_URL` 指向实际用户入口，凭证仍从本人账户服务创建，使用现有stdio命令，不开放新的任意HTTP/SQL/文件代理。`get_workbench` 返回：

- `security.contractVersion = "1.0.0"`
- `security.entryMode = "user-only"`
- `security.administratorCredentials = "rejected"`
- `security.loginRateLimit`：实际窗口、账户/来源次数、密码校验并行上限及进程内计数说明。

HTTP和stdio的OpenAPI/guide资源按入口收敛到用户可用路径。stdio工具注册仍保持现有兼容目录，调用管理工具会得到明确拒绝，不是获得管理权限。

`/api/auth/status` 新增 `entryMode`、`setupAllowed` 和 `security`；未初始化的用户入口 `nextAction` 为 `contact_admin`。用户端口没有单独发布MCP重启代次文件，本轮不承诺用户地址自动热更新目录；升级后用户MCP客户端应在空闲状态手动重载。私有入口已有自动同步机制保留。

这些是只读发现字段，不允许AI修改监听或限流配置。机器契约版本为1.5.18，配置范围/默认值与错误/副作用说明由 `x-http-security` 提供。

## 登录限流语义

- 默认900秒固定窗口，忽略账号大小写，同账号8次、服务端可信请求来源30次；**成功登录也计数**。最多4次并行密码校验。
- 限流在账户服务实施，HTTP调用同一服务；不会只在前端按钮上计数。
- 用户入口和私有入口的账号/IP窗口分开，避免公网尝试直接消耗私有管理入口的窗口；密码校验并行上限属于整个进程。
- 429错误码为 `LOGIN_RATE_LIMITED`，同时返回 `Retry-After` 秒数、`details.retryAfterSeconds` 和请求ID。客户端只显示等待信息，**不自动重试/重放**。
- 来源取Express已验证的请求IP，当前默认未信任代理头。客户端填写 `X-Forwarded-For` 无法直接绕过；同机代理背后的多个用户会共享来源桶，需按实际流量调整来源次数，不能为方便而信任任意转发头。
- 计数是有界的进程内运维状态，不是第二套业务数据库；重启会清空，不能宣称有跨重启或分布式全局限流。容量耗尽拒绝新键，不驱逐尚有效的限制。

## 错误脱敏与对账

用户入口始终脱敏；私有入口在生产模式下也脱敏。未知异常和JSON解析错误不把原始异常、请求内容或堆栈回显到客户端。可操作的4xx业务错误保留code和revision/冲突字段，同时清理消息与details中的路径、URL、凭证和密码等敏感内容。

错误保留响应 `X-Request-ID`，JSON中也返回 `requestId`；UI显示5xx请求ID，stdio MCP继续沿用现有错误包装。不会把失去回执/5xx当成确定没有写入：仍按原ID读取对账，不自动换ID、重复扣写或重放运行/发布。

本人媒体仍走原授权。归档媒体的GET/HEAD/Range复用现有 `authorizeRunMedia`，场景撤权后拒绝媒体读取；本人历史任务的业务元数据仍按已有规则读取。没有改变历史工作流或自动替换已发布场景。

## 上线配置尚需核验（本轮未改）

1. **TLS终止反向代理**：当前原有Origin检查按请求protocol/Host判断，Cookie的Secure依据req.secure。TLS在代理终止、HTTP回源时，仍需独立核验可信代理、固定Origin和Secure Cookie；前次初审已复现默认配置下HTTPS Origin被403拒绝和Cookie缺少Secure。**本改造没有修复该问题，也没有提供已验证可直接用于HTTPS公网的代理配置。** 不能通过删Origin或随意信任转发头来绕过。
2. 防火墙、隧道和反向代理必须实际只公开用户端口。不要另行暴露ComfyUI、Hermes、开发服务器、数据目录或备份。
3. 额度、队列容量、上传总配额/媒体校验、远程抓取与Agent工具权限隔离按当前决定暂不调整。这不是完整公网安全认证，仍有有效用户滥用/资源与执行边界风险。
4. 正式升级仍先核验进程身份、空闲/待审核状态和备份，使用现有安全升级流程；不重启Hermes Gateway或ComfyUI。新增入口需要用户/运维明确配置后生效。
